## What I worked on

Task 12 layered explicit Data API grants and row-level security onto the Task
11 schema. Anonymous clients could read only published catalog data;
authenticated clients could additionally read their own profile and manage
their own rating fields. Aggregate tables and trigger helpers remained
client-read-only or inaccessible.

## Problem discovered

Row-level security alone does not grant access, and table grants alone do not
restrict rows. A secure mobile contract needed both layers to agree, including
column-level limits that prevent clients from rewriting identities, audit
fields, or server-owned aggregates.

## Decision made

The migration revoked broad privileges before rebuilding a narrow allowlist.
Tests then exercised anonymous, owner, cross-user, unpublished-product,
private-note, malformed-claim, and service-role cases. The service-role secret
remained server-only and forbidden from Expo.

## Evidence captured

Pull request #23 and its merge commit record the policy and grant matrix. The
acceptance report records 418 pgTAP assertions, concurrency races, local checks,
and transaction-rolled-back staging authorization tests. Production remained
untouched.

## Result

The database exposed only the capabilities required by the planned client.
The project could proceed to deterministic seed data without weakening the
deny-by-default foundation.

## What I worked on

Task 18 added a forgot-password request screen, a reset-password deep-link
target, recovery-event handling, and focused automated tests. The request
screen returned the same confirmation whether or not the address identified
an account.

## Problem discovered

Password recovery arrives through an asynchronous authentication event and can
race with ordinary session restoration. Treating any user update as recovery
would expose the reset route at the wrong time, while different confirmation
copy could disclose account existence.

## Decision made

The app introduced an explicit recovery phase driven by the authentication
provider's recovery event and routed local/development email links through the
`eazyreview` scheme. Recovery state was guarded separately from normal session
changes, and production host configuration stayed outside the task.

## Evidence captured

Pull request #37 and its merge commit preserve the reviewed implementation.
The evidence report records automated checks and a physical-device recovery
matrix reported as passing, including rejection of the old password. Web and
simulator recovery walks were not run.

## Result

People gained a bounded recovery path without weakening the anonymous catalog
or revealing account membership. The task satisfied Task 19's dependency but
did not authorize deletion work or production setup.

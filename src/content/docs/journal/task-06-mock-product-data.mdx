production catalog records.

## What I worked on

Task 6 created the first typed product contracts and eight mock products. The
fixtures included ordinary products alongside missing Eazy Score and zero-
rating cases so later screens could display honest empty states.

## Problem discovered

A list of uniformly complete sample products would make the happy path look
finished while hiding the states a real catalog inevitably contains. At the
same time, connecting Supabase before the screen flow was understood would
couple product design to backend setup.

## Decision made

The project used deterministic local data with explicit product, card,
breakdown, rating-summary, and offer types. It modeled absence instead of
filling every field with invented values, while leaving network behavior and
durable user state for later tasks.

## Evidence captured

Commit `27dccef07af150855bf699940ef089ec96811c54` records the mock catalog and
its contracts together with the first Browse implementation. The archived task
record identifies eight products and the null-score and zero-rating fixtures.

## Result

The UI could be developed against repeatable data that exposed both complete
and sparse presentation paths. Those fixtures were a design tool, not a second
source of truth for the eventual database.

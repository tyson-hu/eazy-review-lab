## 1. Objective

Create a separate, public, human-readable development lab for Eazy Review. The
lab will turn implementation history, product reasoning, engineering evidence,
and decisions into:

- a concise project overview;
- development-journal entries;
- engineering reports;
- public decision summaries;
- experiments;
- accessible charts and diagrams;
- RSS and JSON feeds that the personal blog can consume; and
- agent-readable Markdown and `llms.txt` surfaces generated by Nimbus.

The work is intentionally split into three reviewable milestones. The first
readable report can be shared privately with reviewers after M2; feeds, full
CI/CD integration, the custom production domain, and the public indexed launch
are an M3 publishing package rather than blockers for writing and reviewing the
report.

## 2. Milestone Contract

| Milestone | Deliverable | Launch gate |
|---|---|---|
| **M1 — Site foundation** | Nimbus scaffold, homepage, five section pages, styling, navigation, search, 404, basic stable-behavior checks, and an unindexed `workers.dev` preview | Site is usable and contains no placeholder copy |
| **M2 — Flagship report** | Immutable raw GitHub snapshot, separate derived classifications, report, deterministic charts, adjacent data tables, methodology, accessibility review, and human editorial approval | Report is accurate, reproducible, and human-approved |
| **M3 — Publishing integration** | RSS, JSON Feed, stable output tests, GitHub workflow, Workers Builds, custom domain, and personal-blog feed contract | Production deployment is healthy at `lab.tianzhe.me` |

Milestone boundaries are review boundaries:

- M1 must not absorb the evidence pipeline.
- M2 must not absorb feed or deployment automation.
- M3 must not silently rewrite the published M2 evidence.

## 3. Fixed Decisions

1. **Use a separate repository.** The lab lives in the current
   `eazy-review-lab` folder and does not become a package inside the Expo app.
2. **Use Nimbus with Astro and pnpm.** Scaffold with Cloudflare deployment
   support and commit the generated lockfile and Nimbus provenance file.
3. **Deploy static output on Cloudflare Workers.** Use the Worker name
   `eazy-review-lab`.
4. **Keep the app repository authoritative.** The adjacent Eazy Review
   repository remains the product and implementation source of truth.
5. **Keep the personal-blog integration simple.** Use curated links plus RSS
   and JSON feeds; do not copy or synchronize article source in version 1.
6. **Keep publication approval in content metadata.** Draft content builds
   successfully but is excluded from production surfaces. Human approval
   changes content metadata; it does not pause an otherwise healthy CI job.
7. **Keep assets local initially.** Commit versioned editorial SVG/WebP assets
   in the lab repository. Defer Cloudflare R2.
8. **Use `lab.tianzhe.me` as the working production-domain assumption.** Stop
   and confirm if the Cloudflare zone or DNS record conflicts with that domain.
9. **Keep normal builds evidence-offline.** Builds and tests inspect only
   committed evidence. Remote existence checks belong to an explicit manual
   refresh command and never run as part of the normal build.

## 4. Authority and Safety Boundaries

### Lab repository

The current folder will own:

- the Nimbus/Astro application;
- public MDX content;
- editorial templates;
- immutable raw evidence snapshots;
- separately reviewed derived classifications;
- generated editorial charts;
- feed endpoints;
- publication validation;
- deployment configuration; and
- lab-specific CI and contributor guidance.

### Eazy Review application repository

Treat `../eazy-review` as read-only while building the lab. It may be inspected
for evidence, but this project must not:

- edit its application code or documentation;
- import files from it at runtime;
- create symlinks into it;
- add a workspace or monorepo relationship;
- rewrite its Git history; or
- change its GitHub pull requests.

When product language is used, preserve these terms exactly:

- `Eazy Score`
- `Community Score`
- `My Rating`

For product facts, begin with the current authoritative documents in the app
repository, including `AGENTS.md`, `docs/BLUEBOOK.md`,
`docs/DOCUMENTATION_POLICY.md`, `docs/DESIGN.md`, and the generated
`docs/DECISIONS.md`. Public writing summarizes dated source material rather than
introducing competing product requirements.

### Public overview boundary

The public project overview must be short. It may paraphrase the Bluebook, but
must not copy large sections or become a second product specification. Pin its
source in frontmatter:

```yaml
sourceRepository: tyson-hu/Eazy-Review
sourceCommit: 9eb485cd9b6207b52ff4408ee89647f32faae436
sourcePath: docs/BLUEBOOK.md
lastVerifiedAt: 2026-07-26
```

Refresh those fields only after reviewing the newer authoritative source.
Product requirements continue to be updated only in the application
repository.

### Evidence boundary

Every numerical or historical report claim must be traceable to:

- an immutable committed raw snapshot;
- a separately committed derived classification; or
- an exact public PR or commit URL.

Separate observed facts, derived calculations, interpretation, and
recommendations. Do not label every review comment as a bug. Do not infer code
quality or reviewer accuracy solely from PR size, sequence, or decomposition.

## 7. M2 — Evidence and Flagship Report

### M2.1 Build an explicit manual evidence refresh

Create a networked manual command such as:

```bash

```

Its responsibilities are:

1. fetch the exact GitHub repository, PR, commit, changed-path, check, and

2. verify remote PR and commit sources exist;
3. normalize and sort the response deterministically;
4. record fetch time, repository, frozen refs, schema version, and verification

5. write a **new** raw snapshot revision; and
6. refuse to overwrite a snapshot used by an already published report unless
   an explicit, reviewed migration path is supplied.

This command is never called by `build`, `check`, CI, or deployment. Authentication
is local/CI-secret state only and is never written to the snapshot.

### M2.4 Source-freeze contract

Evidence used by a published report is immutable:

1. A published report never silently refreshes evidence.
2. A refresh creates a new versioned raw snapshot.
3. Derived files declare the exact raw snapshot revision they interpret.
4. A material evidence change creates a new derived revision and updates the
   report's `lastUpdated`.
5. Report methodology records both the source-freeze date and publication date.
6. Old snapshot and derived files remain available when required to reproduce
   an earlier published version.
7. Reports link to exact PRs and full commit SHAs, never moving branches.
8. A correction note explains material changes to an already published report.

## 10. Source Validation and Offline-Build Contract

Normal build and CI:

- read only repository files and installed dependencies;
- never call GitHub, DNS, HTTP, or Cloudflare APIs for evidence validation;
- validate syntax, allowlists, identifiers, metadata, and internal consistency;
- generate charts only from committed derived data; and
- produce identical editorial data output for the same commit and dependency
  lockfile.

Manual evidence refresh:

- is explicitly invoked;
- may use the network;
- verifies remote existence;
- records results in a new immutable raw snapshot revision; and
- requires human review before derived classifications or published content
  move to the new revision.

Package installation and deployment naturally require external services; the
term "offline build" refers specifically to evidence resolution and content
generation after dependencies are available.

## 12. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| The plan repeats PR #14 by bundling too much | Enforce M1/M2/M3 deliverables and review gates |
| Nimbus is pre-1.0 and its scaffold changes | Inspect live CLI help, retain `nimbus.json`, pin the lockfile, and review scaffold diffs |
| A raw GitHub fact is mixed with editorial judgment | Keep versioned `raw/` and `derived/` files with explicit lineage |
| A published report silently changes | Enforce the source-freeze contract and preserve old revisions |
| A build tries to prove a URL is public | Keep builds offline; remote verification exists only in manual refresh |
| Causal language outruns evidence | Use scoped headings and prohibit quality/accuracy claims without frozen measurements |
| The project overview becomes a stale specification | Keep it short and pin repository, commit, path, and verification date |
| AI provenance becomes contradictory | Derive publishability from `draft`, `aiGenerated`, `humanReviewedAt`, and `reviewedBy` |
| Output tests break on harmless Nimbus upgrades | Test stable public behavior, not hashes or internal directories |
| A preview host is indexed before the canonical domain works | Add preview-only `noindex`, disallow crawling, and test both preview and production output |
| DNS or remote resources already exist | Resolve exact ownership with read-only checks and stop on conflicts |

## 13. Documentation and Upgrade Policy

- Treat lab articles as derived explanations, not replacements for app
  specifications.
- Every meaningful implementation change updates the relevant plan, handoff,
  decision summary, or report—or states why no documentation update is needed.
- Use lockfile-controlled, reviewable upgrades.
- Before upgrading Nimbus:
  1. inspect current release notes and installation docs;
  2. check the live CLI help;
  3. check `pnpm outdated`;
  4. compare a disposable current scaffold with the repository;
  5. preserve local content, evidence, and style decisions;
  6. run clean-install validation; and
  7. review public routes and agent surfaces.
